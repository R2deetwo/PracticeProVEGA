## BUG 1: UNITS DISAPPEAR WHEN EDITING A UNIT (CRITICAL)

**Symptom**: When I edit a unit under a property that has multiple units (e.g., 10 units), all units except one disappear from the UI. After a page refresh, all units return and the edit IS persisted. This happens every time a unit is edited.

**Root Cause**: The `DataProvider.tsx` optimistic update pattern. When `updateItem` is called for a unit edit, it captures `prevState = appState` at call time and then replaces the entire property object in state. Since properties contain nested units arrays, the optimistic update overwrites the full units array with data that only includes the edited unit — the other units are lost from state temporarily. When Convex refreshes the real data, the full units array returns, which is why a refresh fixes it.

**Fix Required**:
1. In `DataProvider.tsx`, fix `updateItem` to do a **deep merge** instead of a shallow replace when updating entities that have nested arrays (especially properties with units). The optimistic update must preserve existing units that aren't being edited.
2. Specifically: when updating a property, the optimistic state should merge the new data into the existing property object, NOT replace it. Use:
   ```
   updatedItem = { ...existingItem, ...updateData }
   ```
   where `existingItem` is the current item from state (not from stale `prevState`).
3. Fix the stale `prevState` capture — use a functional state updater pattern (`setState(prev => ...)`) instead of capturing `appState` at call time, so the update always works against the latest state.
4. For unit-specific edits: if the edit mutation only updates a single unit within a property's units array, the optimistic update should only modify that one unit in the array, not replace the entire array. Map over the existing units array and replace only the unit with the matching ID.

**Files to modify**:
- `src/contexts/DataProvider.tsx` — fix optimistic update logic in `updateItem`
- `src/hooks/useProperties.ts` — ensure unit edit calls pass the full units array (with the edited unit merged in) to `updateItem`, OR add a dedicated `updateUnit` action that only updates one unit within the property

## FEATURE 3: UNIT CARD VISUAL STATUS SYSTEM

**Current Behavior**: All unit cards under the Units tab look the same — same color, same style, no visual distinction. This makes it impossible to scan the list and quickly identify which units need attention, which are commercial vs residential, or which have incomplete data.

**Design Philosophy**: The visual system should communicate three independent dimensions at a glance: (1) what type of unit is this, (2) is the data complete, and (3) is anyone living/operating there. The colors should be **subtle** — background tints and accent borders, not loud or garish. Think professional dashboard, not children's game.

### A. Unit Type Distinction (Base Tint)

Each unit card should have a **subtle background tint** based on unit type:

| Unit Type | Background Tint | Rationale |
|-----------|----------------|-----------|
| **Residential** | Cool blue-slate (#EFF6FF or similar very light blue) | Calm, stable, living spaces — blue conveys trust and permanence |
| **Commercial** | Warm amber-gold (#FFFBEB or similar very light gold) | Business, commerce, professional — warm tones convey activity and enterprise |

This immediately lets the user distinguish unit types when scanning the grid. If the user has a mixed-use property, they can visually separate residential from commercial at a glance.

### B. Data Completeness Status (Left Border Accent)

Each unit card should have a **4px left border** whose color indicates data completeness. This is the most important visual signal — it tells the user "does this unit have what it needs for proper tracking?"

**Critical Fields Hierarchy** (for occupied units):

| Tier | Fields | Why Critical |
|------|--------|-------------|
| **Tier 1 — Must Have** | Tenant name, tenancy start date, tenancy end date | Without these, you cannot track who is in the unit, when they moved in, or when the lease expires. This is legal and financial risk. |
| **Tier 2 — Should Have** | Tenant phone number, rent amount | Phone is critical for communication and emergencies. Rent amount is needed for financial tracking. Missing these creates operational gaps. |
| **Tier 3 — Nice to Have** | Tenant email, unit size, notes | These improve records but are not urgent for tracking or compliance. |

**Status Determination Logic**:

```
if unit is VACANT (no tenant):
    status = "vacant" → grey border (#D1D5DB)

if unit is OCCUPIED:
    if ALL Tier 1 AND Tier 2 fields are present:
        status = "complete" → green border (#22C55E)
    else if any Tier 1 field is missing:
        status = "critical" → red border (#EF4444)
    else if Tier 1 is complete but any Tier 2 field is missing:
        status = "partial" → amber border (#F59E0B)
```

**Rationale for each status**:
- **🟢 Complete (green)**: This unit is fully tracked. The landlord/manager can reach the tenant, knows when the lease ends, and has all critical data. No action needed.
- **🟡 Partial (amber)**: Most critical data is there, but something operational is missing — typically a phone number or rent amount. The user should fill this in when convenient. Not urgent but should not be ignored.
- **🔴 Critical (red)**: This unit is occupied but missing fundamental tracking data. A tenant is living there without a recorded lease start/end, or the tenant's name is unknown. This is a legal and financial risk — imagine trying to enforce a lease without knowing when it started or ends. The user needs to address this.
- **⚪ Vacant (grey)**: No tenant, so most fields are irrelevant. This unit needs a tenant, not data. Grey is neutral — it's not a problem, it's an opportunity.

Each unit card should follow this layout (top to bottom):

## CRITICAL: VERCEL BUILD PREVENTION

**⚠️ DO NOT regenerate `package-lock.json` using `npm install` inside Replit.** Replit's npm proxy bakes internal URLs into the lockfile that break Vercel builds.

**The Problem**: Replit routes npm through `http://package-firewall.replit.local/npm/...`. This URL gets written into `package-lock.json` under the `"resolved"` field. Vercel's build servers cannot resolve `package-firewall.replit.local` and the build fails with `ENOTFOUND`.

**Prevention Rules**:
1. **Never run `npm install`** for adding packages. Use `npm install --package-lock-only=false` or manually add packages to `package.json` and let the user install locally.
2. If you MUST run `npm install`, immediately run this after:
   ```bash
   sed -i 's|http://package-firewall.replit.local/npm/|https://registry.npmjs.org/|g' package-lock.json
   ```
3. Before any `git push`, verify the lockfile is clean:
   ```bash
   grep -c "package-firewall.replit.local" package-lock.json
   ```
   If the count is > 0, run the `sed` command above.
4. Consider adding this as a git pre-push hook or a script in `package.json`.
